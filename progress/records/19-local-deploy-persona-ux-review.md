## 요청과 점검 방식

사용자 요청은 로컬 재배포 후 실제 브라우저에서 여러 사용자의 서비스 흐름을 확인하고, 복잡해서 이용을 포기할 만한 지점을 찾는 것이다. 이번에는 제품 소스를 수정하지 않았다. 기존 미커밋 변경을 유지하고 배포·관찰·개선 후보 기록만 수행했다.

computer-use의 Browser Use로 홈 → 비회원 선택/설문 → 결과 → 입력 수정, 주택 유형 모름, 로그인/가입 → 이전 결과 → 상세/삭제 취소, 독립 챗봇 → 후속 질문/새로고침 → 초기화 취소/로그아웃을 확인했다. PC 1440×900과 모바일 360×800에서 실제 게시 카탈로그 `m08a-20261004-v2`와 로컬 DB를 사용했다. 모의 API 시험과 구분한다.

아래 페르소나는 전문가의 가상 과업 점검이다. 실제 연령별 참가자를 모집하거나 성공률·소요 시간을 측정한 사용자 조사는 아니다. 재현한 동작과 특정 집단에 미칠 영향에 대한 추정을 구분했다. P1은 핵심 과업의 진행을 막거나 사용자가 스스로 복구하기 어려운 문제, P2는 안내 이해·신뢰·재사용을 떨어뜨리는 문제다.

## 먼저 해결할 진행 장애

### UX01 · P1 · 로그인 후 이전 결과 화면이 계속 대기

- 재현: 비회원으로 ‘이전 결과’ → ‘로그인하기’ → 로그인 완료. 메뉴는 ‘로그아웃’으로 바뀌지만 본문은 ‘정보를 확인하고 있어요.’에 머물렀다. 신규 가입 후 로그인과 기존 테스트 계정의 재로그인에서 각각 재현했다. 첫 관찰에서는 30초 넘게 기다려도 진행되지 않았다.
- 복구: 새로고침하면 목록이 열렸다. 로그인/회원 확인 API는 성공했지만 멈춘 전환에서 이력 조회 요청이 이어지지 않은 서버 로그를 확인했다. 현재 자료만으로 인증 서버 실패로 단정하지 않는다.
- 영향: 모든 회원 이용자의 결과 재접근을 막는다. 익숙하지 않은 이용자는 새로고침이 복구 방법인지 알 수 없다.
- 최소 수정 후보: 인증 전환 시 캐시 정리와 활성 조회의 순서를 점검하고 회원 화면 조회가 반드시 다시 시작되게 한다. `useAuth`의 사용자 변경 효과와 `clearMemberCache`의 조회 제거가 원인 후보이며 확정 원인은 아직 조사하지 않았다. 계정 사이 데이터 격리를 유지해야 한다.
- 확인 조건: 비회원 게이트에서 로그인 후 새로고침 없이 이력/챗봇이 열리는 실제 브라우저 회귀.
- 증거: [첫 대기](../../artifacts/ux-20261019/11-history-login-stuck.png), [재로그인 재현](../../artifacts/ux-20261019/18-login-stuck-repeat.png), [새로고침 복구](../../artifacts/ux-20261019/12-history-after-reload.png). 관련 코드: [인증 전환](../../frontend/src/features/auth/state.ts), [사용자 변경 효과](../../frontend/src/features/auth/useAuth.ts), [이력 화면](../../frontend/src/pages/History.tsx).

### UX02 · P1 · 다음 단계가 화면 중간에서 열려 안전·필수 질문을 놓침

- 재현: 모바일 선택 화면 하단 ‘저장하고 설문으로’ 클릭 직후 스크롤 위치 1,008px, 설문 제목 상단 좌표 -773.2px였다. 첫 화면에는 세 번째 필수 질문과 결과 버튼이 보이고 앞의 안전·사용 상태 질문은 화면 위에 가려졌다. PC의 설문 → 결과도 스크롤 764.8px와 제목 -477px를 관찰했다.
- 영향: 새 단계의 시작을 인지하기 어렵고 보이지 않은 필수 질문을 답하지 못한다. 고령층·작은 화면·키보드 이용자에게 특히 복구가 어렵다고 예상한다.
- 최소 수정 후보: 앞으로 단계가 바뀔 때 제목으로 스크롤과 초점을 이동한다. 브라우저 뒤로 가기의 의도한 위치 복원은 별도로 확인한다.
- 확인 조건: 화면을 충분히 내린 뒤 다음 단계로 이동해 제목과 첫 질문이 실제 뷰포트 안에 있는지 검사.
- 증거: [모바일 설문 진입 화면](../../artifacts/ux-20261019/07-mobile-survey-landing.png). [라우팅](../../frontend/src/App.tsx)에 단계 전환 위치 복구가 없는 점을 소스에서 확인했다.

### UX03 · P1 · 필수 답변 누락과 ‘모름’의 복구 경로가 불명확

- 재현 A: LH/주방/배관/누수를 선택하고 필수 질문을 하나도 답하지 않아도 ‘안내 결과 확인’을 누를 수 있었다. 결과는 ‘추가 정보 필요’와 포괄적인 재확인 문구만 표시했다. ‘입력 수정’은 빠진 설문 항목 대신 첫 주택·증상 선택 화면으로 돌아갔다.
- 재현 B: 주택 유형을 모른다고 선택한 뒤 표시된 질문을 모두 답해도 ‘주택 유형을 확인해 주세요’가 나왔다. 화면에는 주택 유형을 확인할 방법이나 모르는 상태에서 할 수 있는 다음 행동이 없었다.
- 영향: 질문을 빠뜨린 사람과 실제로 답을 모르는 사람이 같은 재시도 경로를 반복할 수 있다. ‘모름’ 선택을 허용해 놓고 이후 이용 방법을 제공하지 못한다.
- 최소 수정 후보: 무응답과 유효한 ‘모름’을 구분한다. 무응답이면 해당 질문 옆에 알리고 첫 누락 항목으로 이동한다. 주택 유형을 모르면 확인할 자료/문의 내용을 안내한다. 결과의 수정 버튼은 부족한 항목으로 바로 연결한다.
- 증거: [무응답 결과](../../artifacts/ux-20261019/03-unanswered-result.png), [모르는 주택의 결과](../../artifacts/ux-20261019/08-unknown-housing-result.png). 관련 화면: [설문](../../frontend/src/pages/Survey.tsx), [결과](../../frontend/src/pages/Result.tsx).

### UX04 · P1 · 생활 속 증상을 찾으려면 시설 분류를 먼저 알아야 함

- 재현: ‘주방 → 싱크대 하부·뒤쪽’의 증상은 ‘싱크대 아래·뒤쪽 마감이 없어요’와 ‘증상을 잘 모르겠어요’뿐이었다. 물이 새는 사람은 시설을 ‘급수·온수·배수 배관’으로 바꿔야 ‘물이 새거나 물 자국이 있어요’를 찾을 수 있었다.
- 영향: 웹에 익숙해도 시설 전문 분류를 모르면 맞는 증상이 없다고 판단하고 이탈할 수 있다. 여러 비슷한 시설 이름 사이를 추측해서 이동해야 한다.
- 최소 수정 후보: ‘싱크대 하부·뒤쪽’이 마감 항목임을 풀어 쓰고 누수를 찾는 경우 기존 배관 항목으로 연결한다. 기존 검토 ID를 유지한 채 증상 예시·설명·별칭을 개선한다. 새 법적 기준을 임의로 만들지 않는다.
- 증거: [싱크대 선택과 증상 불일치](../../artifacts/ux-20261019/02-sink-selection-mismatch.png). 관련 화면: [선택](../../frontend/src/pages/Select.tsx).

### UX06 · P1 · 챗봇이 이미 설명한 시설·증상을 다시 물음

- 재현: ‘싱크대 아래에서 물이 새요. 어떻게 해야 하나요?’에 주택 유형과 시설/증상을 질문했다. 이어 별도 세션에서 ‘LH 건설임대주택이에요. 주방 싱크대 아래 배관에서 물이 새요.’를 입력해도 ‘어떤 시설물에 어떤 증상이 있는지’ 다시 물었다.
- 비교: 같은 누수를 메뉴의 정확한 표현인 ‘급수·온수·배수 배관’, ‘물이 새거나 물 자국이 있어요’로 바꾸자 ‘담당 기관 확인 필요’ 안내로 진행했다. 이후 ‘제10조에서 배관 누수와 관련해 어떤 내용을 확인할 수 있나요?’에는 ‘근거 확인 답변’과 조문/별표가 표시됐다. 챗봇 전체가 응답하지 않는 문제는 아니며 생활 표현에서 분류로 연결되는 구간의 장벽이다.
- 영향: ‘편하게 물어보세요’로 들어온 사용자가 시스템 용어를 알아야 한다. 이미 말한 내용을 다시 물을 때 어떤 표현으로 고쳐야 하는지도 알 수 없다.
- 최소 수정 후보: 인식한 주택/위치/증상을 보여 주고 부족한 항목만 선택지로 확인한다. 검토된 별칭과 일상 표현 예시를 보완한다. 설문과 독립인 기존 챗봇 정책을 유지한다.
- 증거: [첫 추가 확인](../../artifacts/ux-20261019/14-chat-clarification.png), [정확한 메뉴 용어 입력 후 진행](../../artifacts/ux-20261019/22-chat-exact-terms-result.png). 관련 코드: [맥락 추출](../../backend/app/services/chat_context.py).

## 다음으로 개선할 이해·재사용 문제

### UX05 · P2 · 결과를 읽은 뒤 무엇을 하면 되는지 부족

필수 답변을 완료한 누수 설문의 결과는 ‘담당 기관 확인 필요’였다. LH 운영 근거가 없어 보수·비용·교체를 단정하지 않는 것은 기존 제한이며 오류로 보지 않는다. 다만 ‘직접 문의할 내용’은 선택한 공간·시설·증상을 반영하지 않은 ‘보수 대상과 증상을 확인하고 필요한 절차를 안내해 주세요.’였다. 사용자 입장에서는 기관에 무엇을 설명할지 다시 작성해야 한다.

저장/보관 안내·선택 요약·긴 설문 질문/답변이 실제 안내보다 앞서고 모바일에서는 긴 스크롤이 필요했다. 챗봇의 조문 설명도 제10조와 별표 전체가 한 문단으로 표시돼 표의 조건을 비교하기 어렵다. 입력 예시는 ‘제10조 내용을 알려 주세요’여서 기준을 모르는 방문자에게 어렵다.

최소 개선은 결과 맨 위에 ‘지금 할 일’과 입력한 증상을 반영한 문의 문장을 두고 복사할 수 있게 하는 것이다. 질문 상세·보관 설명·출처는 필요할 때 펼쳐 읽게 하고, 법령 원문과 별표는 조건과 단서를 보존하면서 문단/표로 구분한다. 검토되지 않은 법적 요약이나 연락처를 생성하지 않는다. [PC 결과](../../artifacts/ux-20261019/04-leak-result-desktop.png), [모바일 결과](../../artifacts/ux-20261019/05-leak-result-mobile.png), [모바일 조문](../../artifacts/ux-20261019/23-chat-law-wall-mobile.png). 관련 화면: [결과 표시](../../frontend/src/components/ResultView.tsx), [챗봇](../../frontend/src/pages/Chat.tsx).

### UX07 · P2 · ‘저장’의 의미와 회원 전환 기대가 다름

비회원 결과는 현재 익명 상담에 저장됐다고 표시되지만 ‘이전 결과’는 회원 전용이고 회원 가입 후 비회원 기록이 자동으로 옮겨지지 않는다. 보관 만료일과 현재 창에서 다시 열 수 있는 조건도 같은 개념이 아니다. 로그인 뒤 빈 목록은 현재 정책상 정상이어도 사용자는 저장한 기록이 사라졌다고 오해할 수 있다. 챗봇은 같은 로그인 상태의 새로고침에서 세 문답이 복원됐지만 로그아웃·재로그인 후에는 새 빈 대화로 열렸다.

회원 가입 성공 뒤 로그인 화면에서 비밀번호를 다시 입력하는 절차도 확인했다. 잘못된 짧은 비밀번호 안내와 초점 이동은 정상이다. 저장 위치/접근 조건과 회원 전환 시 기록 처리를 시작 전에 쉽게 설명하고, 가입 후 재입력을 줄일 수 있는지는 인증 정책과 함께 검토한다. 자동 이관을 이번 점검의 확정 요구로 만들지 않는다. [비회원 이력 게이트](../../artifacts/ux-20261019/09-guest-history-gate.png), [가입 후 재로그인](../../artifacts/ux-20261019/10-signup-login-again.png), [재로그인 후 빈 대화](../../artifacts/ux-20261019/19-chat-after-relogin.png).

### UX08 · P2 · 삭제 확인을 열 때 키보드 초점 소실

본인 결과 상세에서 ‘이 결과 삭제’를 누르면 원래 버튼이 사라지면서 활성 요소가 BODY가 됐다. 삭제 확인 영역으로 초점이 이동하지 않아 키보드 이용자는 현재 위치를 잃는다. 확인 영역으로 초점을 옮기고 취소 후 원래 조작점으로 돌아오게 하는 작은 보완이 필요하다. 최종 ‘삭제 확인’은 누르지 않고 취소했다. 챗봇 초기화 취소 후에는 입력창으로 초점이 돌아오는 정상 동작을 확인했다. ## 정상 흐름과 검증 범위

- 비회원이 가입 없이 설문을 시작할 수 있고 홈의 두 진입 선택지가 구분된다.
- 안전 질문에 위험 상황으로 답하면 나머지 설문을 계속 요구하지 않고 즉시 ‘안전 확인 우선’ 결과로 이동했다. 회원 결과가 이력에 나타나고 상세 열기도 정상이다. [안전 결과](../../artifacts/ux-20261019/16-safety-result-desktop.png).
- 본인 결과 목록/상세, 로그아웃 후 회원 기능 차단, 잘못된 비밀번호 길이 안내, 삭제/초기화의 취소 경로를 확인했다. 결과 삭제·챗봇 초기화의 최종 실행은 하지 않았다.
- 실제 OpenAI 설정에서 승인된 가상 누수 문답과 조문 설명을 확인했다. 조문 요청은 ‘근거 확인 답변’(`GROUNDED`)으로 완료했고 같은 로그인 상태에서 새로고침 후 복원됐다. 이는 한 상황의 실제 호출 관찰이며 전체 생성 품질·정확도 재평가가 아니다. 실제 개인정보는 입력하지 않았다.
- 최초 외부 전송 시도는 자동 승인 검토가 구체적 승인을 요구해 차단했다. 사용자에게 전송할 가상 문장과 설정된 OpenAI 목적지를 설명했고, 사용자가 동일 범위 후속 질문까지 허용한 뒤 진행했다. 서비스는 원문 전체 대신 선택 라벨·질문 목적·조문 위치와 검토 자료를 보내는 기존 경로를 유지했다.
- `scripts/smoke_api.py --url http://localhost:8080 --rag-ready --catalog-version m08a-20261004-v2`로 기본 web/준비 상태/카탈로그/비회원 인증/오류 응답을 점검했다. 실행 결과와 최종 문서 검사는 아래 검증 기록을 따른다.

캡처 23개와 안전한 건수 JSON은 로컬 전용 [증거 폴더](../../artifacts/ux-20261019/)에 있다. 비밀번호·키는 캡처/보고서에 넣지 않았다. 브라우저는 로그아웃한 홈으로 돌리고 임시 화면 크기 설정을 해제했다. 로컬 서비스는 실행 상태로 남겼다.

최종 기본 API 점검은 `Smoke checks passed: web, live, ready, catalog state, auth, API errors`로 종료 코드 0을 확인했다. 샌드박스의 로컬 포트 접근 제한으로 일반 권한 실행은 실패했으며 허용된 권한에서 통과한 결과다. 문서 색인 생성과 검사는 Markdown 44개·기록 19개를 통과했고 `git diff --check`도 통과했다. 제품 소스 변경이 없어 새 단위 테스트는 작성하지 않았다.

## 한계와 후속

실제 모바일 기기·Safari/Firefox·스크린리더·실제 고령층 사용자 조사는 미실행이다. 브라우저 확대 단축키는 배율 변화가 확인되지 않아 200% 확대 검증으로 인정하지 않는다. `15-desktop-keyboard-check.png`는 일반 PC 화면의 키보드 확인 자료다. 전체 백엔드/프론트 회귀·axe 재실행·장시간 부하·장애 복구는 수행하지 않았다. 빌드·기본 API·실제 브라우저 과업 관찰을 그 검사들의 대체 증거로 해석하지 않는다.
