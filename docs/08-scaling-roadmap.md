# 확장 기준과 구현 순서

작성: 2026-10-03 · 상태: 구현 전 설계

상위 문서: [전체 안내](README.md) · 연계: [설계 결정과 단순화 기록](07-architecture-decisions.md), [QA·운영](06-qa-operations.md)

이 문서는 초기 구성에서 확장이 필요한 조건과 구현 순서를 기록한다. 성능 수치·시험 방법은 QA·운영 설계를 기준으로 하며 실제 측정 결과로 구조 변경 여부를 결정한다.

## 1. 확장 조건과 순서

| 측정된 문제·요구 | 먼저 할 일 | 그 뒤 검토 |
| --- | --- | --- |
| 벡터 검색 지연이 지속적으로 목표를 초과 | 쿼리·필터·DB 자원 측정 | HNSW, 필요 시 재순위 |
| API 1개 워커의 동시 처리 한계 | 외부 호출·DB 지연과 자원 측정 | 다중 워커와 DB 기반 실행 잠금·공유 사용량 제한 |
| 문서 배치가 오래 걸리거나 중단 재시도가 빈번 | 일회성 배치 재실행·실패 기록 | 작업 큐·별도 워커 |
| 통계 조회가 업무 API에 영향을 줌 | GROUP BY 계획·인덱스 확인 | 집계 테이블·분석 작업 분리 |
| DB 자원 경쟁·독립 확장 요구가 분명함 | 인덱스·자원 증설·관리형 DB 비교 | RAG DB 분리 |
| 무중단·고가용성 계약이 생김 | 백업·복구 실측·관리형 DB 검토 | 복제·다중 서버 배포 |

특정 사용자 수만으로 구조를 분리하지 않는다. 초기 목표는 06에 정의하고 실제 지연·오류·비용으로 결정한다.

구현 순서는 완성 목록·API 계약 → 로그인·설문·결과/이력·단일 DB → 사용자 지시 후 원문 전체 정리 → 조 청킹·pgvector·OpenAI 챗봇 → Docker 출시·삭제·복구 검증이다. 우선 기능과 데이터 경계를 완성하고 확장 항목은 근거가 생길 때 추가한다.

실행할 MVP 작업의 순서·선행 조건·완료 기준·진행 상태는 [MVP 개발 진행 안내](../progress/README.md)에서 관리한다.
