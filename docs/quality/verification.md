# QA·운영 역할 설계 — Docker Compose

상위 문서: [전체 안내](../README.md) · 연계: [API](../backend/api.md), [DB](../data/database.md), [RAG](../ai/rag.md)

## 1. 책임과 검증 범위

QA는 권한·저장·단일 DB·RAG 선행·자료 완전성·보존·삭제·복구를 검증한다. 실행 절차는 [보존·백업](../operations/retention-backup.md)과 [배포](../operations/deployment.md)를 따른다. 실제 판정과 미완료 항목은 로컬 `progress/current-status.md`에서 관리한다.

[2026-11-19 출시 전 점검](release-review-2026-11-19.md)에 재현한 경계 사례와 남은 조치를 기록했다.

초기에는 한 서버에서 Docker Compose로 운영한다. Kubernetes·Swarm·여러 서버·별도 Redis·Celery·상시 배치 워커·관측 전용 스택을 도입하지 않는다. 운영 담당자·사업자·서버 사양·도메인은 배포 인수 전에 확정한다.

## 2. Docker의 최소 구성

| 상시 서비스 | 역할·구성 | 외부 포트·데이터 |
| --- | --- | --- |
| web | 다단계 빌드한 React 정적 파일, Caddy HTTPS, /api·/health 프록시 | 80/443만 공개; 인증서·Caddy 데이터 볼륨 |
| api | FastAPI·OpenAI 연동, 초기 1개 워커 | 컨테이너 내부 포트만; DB·키는 서버 설정 |
| db | pgvector가 설치된 PostgreSQL | 5432 외부 공개 없음; 영속 DB 볼륨 |

web의 프록시는 /api/v1과 /health 경로를 그대로 API에 전달한다. 실제 도메인·DNS·80/443 접근 조건을 설정하고 HTTPS 인증서를 갱신한다. [Caddy 공식 안내](https://caddyserver.com/docs/automatic-https)

운영은 소스 폴더 bind mount 없이 빌드한 이미지를 사용한다. API와 DB 이미지·pgvector 버전은 검증 후 고정 태그와 digest로 기록한다. restart 정책과 로그 회전·디스크 용량 점검을 설정한다. 인증서와 DB의 named volume은 컨테이너 재생성 뒤에도 유지하며 운영에서 볼륨 삭제 옵션을 사용하지 않는다. [Compose 운영 안내](https://docs.docker.com/compose/how-tos/production/)

DB healthcheck는 pg_isready를 사용하고 API 시작은 depends_on의 condition: service_healthy 뒤로 둔다. 이는 시작 순서 제어이며 실행 중 DB 장애를 복구해 주지는 않는다. migration 성공과 API readiness도 따로 확인한다. [Compose 시작 순서](https://docs.docker.com/compose/how-tos/startup-order/)

마이그레이션·자료 반입·임베딩·게시·만료 정리는 **같은 API 이미지의 일회성 명령**으로 실행한다. 전용 상시 컨테이너·큐는 없다. 매일 백업·정리 명령을 실행하는 호스트 스케줄러를 사용하고 출력에 완료 시각·건수·오류만 기록한다. 승인된 자료 파일만 관리 명령에 읽기 전용으로 전달하고 웹 경로에 노출하지 않는다.

OpenAI 키·DB 비밀번호는 서버의 접근 제한 설정 파일 또는 제공자의 비밀 주입 기능으로 전달한다. 예시 설정에는 키 이름만 두고 실제 값을 저장소·프론트 이미지·로그에 넣지 않는다. API는 DB superuser를 쓰지 않으며 확장 설치·migration 권한은 관리 명령에 한정한다.

## 3. 환경·설정

| 환경 | 데이터·OpenAI | 목적 |
| --- | --- | --- |
| 자동 개발 시험 | 격리 시험 DB의 합성 fixture, OpenAI mock/OFF | 권한·상담·이력·자료 부족 흐름 |
| CI | 실제 PostgreSQL + pgvector 테스트 DB, 고정 fixture | FK·migration·벡터·중복 검증 |
| 검증 | 완성 목록·검토한 전체 원문·비용 제한 API | 실제 검색·답변 평가 |
| 운영 | 승인·게시 지식, 서버 OpenAI 키 | 실제 서비스 |

합성 fixture는 자동 시험에서만 사용하고 개발 공개 카탈로그·운영 목록의 대체재로 게시하지 않는다. 완성 목록이 없으면 CATALOG_NOT_READY다. 실제 원문 추출은 사용자 지시 후 컴퓨터 유즈로 수행하며 주기 웹 수집을 만들지 않는다.

주요 설정은 DATABASE_URL 하나와 OPENAI_API_KEY, OPENAI_CHAT_MODEL, OPENAI_EMBEDDING_MODEL, EMBEDDING_DIMENSIONS, OPENAI_ENABLED, SESSION_TTL_HOURS, AUTH_TTL_HOURS, QUESTION_RETENTION_YEARS, MEMBER_RESULT_RETENTION_YEARS, WEB_ORIGINS, 입력·시간·사용량 제한이다. API 워커 수는 초기 1로 고정한다.

질문·회원 결과 보존은 3~5년 범위로 검증하고 기본 5년이다. 활성 임베딩 모델·차원을 지식 묶음과 일치시킨다. DB 연결·스키마 준비와 카탈로그/지식 게시 여부를 구분한다.

## 4. 필요한 검증

| 계층 | 도구·주요 검사 |
| --- | --- |
| 프론트 | TypeScript·ESLint, Vitest·React DOM: 로그인·목록 미완성·이력·오류 |
| API | pytest·HTTPX: 인증·CSRF·소유권·중복 응답·실패 |
| DB | 실제 pgvector PostgreSQL: migration·FK·정확 검색·기한·삭제 |
| E2E | Playwright: 설문·회원 챗봇·이력·로그아웃·키보드 |
| AI | 고정 평가셋: RAG 선행·별표 연결·무근거 생성 차단·인용·연락처 |
| 운영 | 이미지 시작·단일 워커 재시작·백업 복원·삭제 적용 |

CI는 정적 검사 → 도메인·권한 → 단일 DB migration·fixture → API·OpenAPI 타입 → 핵심 E2E → 이미지 smoke로 구성한다. DB 특성 검증에 SQLite를 대신 쓰지 않는다. 매 커밋 실제 OpenAI API를 호출하지 않으며 자료·모델·프롬프트 변경 및 출시 때 비용 제한 평가를 수행한다. 구현을 그대로 반복하는 시험 대신 권한·정합성·오류 경계를 검증한다.

| F32 | 초기화 전후 로그인·설문·이력·질문 보존·사용량·백업 복원 | 로그인·SURVEY·결과 이력·장기 정제 질문·chat_usage 유지; 종료한 원본 대화는 삭제/복원 후 재노출 없음; 보존 범위 고지 일치 |
| F33 | 외부 링크를 열지 않는 답변·근거 확인 | 답변·조건·주의사항/확인 질문과 원문 excerpt·자료 위치를 사이트 내에서 확인; 링크만 안내하거나 설문 화면으로 넘기면 실패; 원문 링크는 선택적 |
| F34 | 미로그인·타인 초기화·CSRF·독립 채팅의 RAG 회귀 | 서버 권한·소유권·Origin/CSRF 유지; 내부 검색 선행·위험 우선순위·운영 근거 게이트·연락처 금지·중복 방지와 excerpt 조건/단서 보존 검증 |
| F35 | 사용자가 고른 설문 불러오기 | 선택/실행 전 자동 조회·복사 없음; 본인 결과·동일 카탈로그·기한·CSRF·잠금·revision 확인; 자유 설명 제외·답변 라벨만 외부 투영·위험 우선·원래 설문 독립 유지 |

F13~F14 시험만으로 실제 원문 추출 완료를 보고하지 않는다. 지시 전에는 합성 자료로 검토 게이트만 시험하고 지시 후 확보한 원문을 대조한다.

| 모델 문맥 | 최근 6개 메시지·적격 근거 최대 5개 묶음 |
| 비용 | 호출별 출력 상한·사용량 관측·일일 예산 경보 |

회원 채팅은 chat_usage의 신규 예약을 기준으로 확인해 상담 삭제·API 재시작으로 한도가 초기화되지 않는다. 로그인·가입은 이메일별 10회/10분·주소별 60회/10분의 단일 프로세스 시도 제한을 적용한다. 인증 시도 카운터는 재시작하면 초기화된다. 완료 응답 재생은 다시 차감하지 않으며 실패 후 새 ID로 호출하면 실제 사용량에 반영한다.

`SESSION_CREATE_WINDOW_LIMIT`, `SURVEY_SESSION_WINDOW_LIMIT`, `SURVEY_DAILY_LIMIT`으로 조정한다. 설문 검색 예약은 PostgreSQL에 유지하며 원문, 계정, 주소를 저장하지 않는다. 안전·범위·정보 부족 안내는 임베딩 예약 전 처리한다. 8080과 운영 HTTPS의 API 프록시는 요청 본문을 64KB로 제한한다. 터널을 통해 들어오는 여러 방문자는 프록시에서 보이는 주소 한도를 공유할 수 있다.

일일 비용은 OpenAI 사용량과 API 관측으로 확인하고 임계치를 넘으면 생성 기능을 중단할 수 있게 한다. 경보·과금 반영에 지연이 있으므로 정확한 금액 상한을 보장한다고 설명하지 않는다. OpenAI OFF·예산 중단 시 추측하지 않고 기본 안내를 제공한다. 질문을 벡터화할 수 없으면 세부 안내를 중단하며 외부 검색으로 우회하지 않는다.

360px·확대·키보드·스크린리더에서 설문·로그인·챗봇·이력·삭제를 검토한다. 상태 설명·질문 라벨·초점·대화 알림·복사 실패 대안을 제공한다. 자동 접근성 검사와 수동 검토를 함께 수행한다.

## 6. 보존·삭제·백업

| 데이터 | 보존안 | 적용 |
| --- | --- | --- |
| 상담·계정 인증 세션 | 24시간 | 인증 만료 뒤 재로그인으로 이력 조회 가능 |
| 원본 상담·대화·요청 응답·비회원 결과 | 상담 만료 후 7일 이내 정리 | 비회원 현재 조회는 24시간만 |
| 회원 결과 이력 | 기본 5년, 3~5년 설정 | 생성 당시 입력·답변·출처 스냅샷 |
| 정제 질문·검색 통계 원본 | 기본 5년, 3년 시점 활용 검토 | 양쪽 사용자; GROUP BY로 통계 조회 |
| 운영 로그 | 14일 | 원본 입력·대화·비밀번호·토큰 없음 |
| 단일 DB·검토 파일 암호화 일일 백업 | 14일 | 장기 데이터 보존 기간과 구분 |
| 최신 삭제 로그 | 15일 | 복원한 백업에 명시적 삭제 재적용 |
| 지식 원문·manifest·검토·철회 | 버전 보존 | 사용자 질문과 구분 |

질문에는 식별정보를 제거하고 필요한 선택·답·정제 질문만 남긴다. 데이터 양·활용·기간을 매년 점검하며 기본 5년을 자동 연장하지 않는다. 사용자 질문을 RAG 지식이나 모델 학습 데이터에 자동 편입하지 않는다.

상담 종료는 계정 이력·정제 질문 삭제와 구분한다. 명시적 삭제는 즉시 DB에 반영하고 관련 응답 캐시도 제거한다. 통계는 원본 GROUP BY이므로 별도 집계 보정이 없다. 익명 사용자는 유효한 현재 토큰으로 eraseRecords=true를 요청할 수 있다. 만료 토큰으로 익명 과거 기록을 추측해 조회하지 않는다.

결과 삭제 때 요청 행까지 지우지 않는다. 결과·연결 질문·응답 본문 삭제와 요청의 DELETED 전환·삭제 로그 저장을 같은 트랜잭션으로 수행한다. 본문 없는 요청 기록은 상담 정리까지 남겨 동일 ID 재실행을 막는다. 질문 기록만 삭제할 때는 기존 결과를 유지하며 완료 응답 재생으로 질문 기록이 복원되지 않는지 확인한다. 백업 복원 시 결과를 삭제하기 전에 연결 요청을 찾아 DELETED와 response_json=null도 적용한다.

매일 pg_dump로 한 DB의 일관된 백업을 만들고 검토 파일·manifest도 함께 보관한다. 실행 성공·크기·보존 정리·원격 저장 완료를 확인하며 별도의 서버 또는 접근 제한 저장소에 암호화해 둔다. Docker 볼륨·컨테이너 이미지만으로 백업을 대신하지 않는다. [PostgreSQL pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html)

deletion_log는 본문 없이 대상 ID·종류·시각만 저장한다. 삭제 직후 및 백업 전에 최신본을 작은 암호화 파일로 별도 보관하고 실패하면 알림·재실행한다. 전용 복제 서비스는 두지 않는다. 복원 시 최신 삭제 파일·retained_until·단기 만료를 적용한 뒤 공개한다. 최신 삭제 파일이 없거나 미반영 삭제 여부를 확인할 수 없으면 회원 이력·질문 복원본 공개를 보류하고 필요하면 해당 데이터를 복구 대상에서 제외한다. 이 절차 없이 삭제 재등장 방지를 보장한다고 하지 않는다.

OpenAI의 전송·보존 설정은 자체 3~5년 보존과 별개다. store=false를 제공자 전체 보존 0으로 설명하지 않으며 전송 고지·프로젝트 설정을 확인한다. [OpenAI 데이터 제어](https://developers.openai.com/api/docs/guides/your-data)

## 7. 배포·관측·복구

배포는 백업 확인 → 이전 API 완전 종료 → DB 준비 → 같은 이미지의 migration 1회 → 새 API 중단 요청 정리 → web·API smoke 순서로 진행한다. 이미지 교체 중 짧은 점검 중단을 허용한다. 초기 구성에서 겹치는 API 프로세스·무중단 배포는 사용하지 않는다. DB migration을 각 API 시작 때 경쟁 실행하지 않는다.

live는 프로세스 생존, ready는 DB·필수 설정·중단 요청 정리를 확인한다. catalogReady=false는 준비 중 상태이며 상담 시작만 차단한다. ragReady=false·OpenAI 비활성은 DB가 정상일 때 기본 안내로 처리한다. DB 장애·실패 요청 정리 미완료는 ready 503이다. health 응답은 비밀·내부 주소를 포함하지 않는다. Compose의 healthcheck만으로 고가용성·장애 재시작이 보장되지는 않는다.

초기 관측은 구조화 로그·HTTP 지연·오류율·DB 연결/검색 시간·상태별 응답 수·OpenAI 사용량·차단 사유·백업/정리 성공 시각·디스크 용량으로 충분하다. 전체 질문·답변·비밀은 로그에 넣지 않는다. 별도 관측 서버는 실제 필요가 생길 때 도입한다.

복구는 점검 상태에서 백업을 새 DB에 복원하고 schema·pgvector·삭제/기한·계정 이력·인용을 확인한 뒤 연결한다. 지식 원문은 최신 승인·철회 상태를 검토하기 전 현재 안내 근거로 활성화하지 않는다. 벡터는 검토 완료 원문으로 재생성할 수 있지만 장기 질문·회원 이력은 백업이 필요하다.

RPO 24시간·RTO 4시간은 기존 목표를 유지하며 달성 보장은 아니다. 출시 전에 실제 복원 시간을 측정한다. 이전 API 이미지로의 되돌리기는 스키마 호환을 확인한 경우에만 수행하며 파괴적 DB 변경은 별도 이전 계획을 작성한다.

## 8. 출시 조건과 확장 조건

- F01~F34(F10a~F10c 포함)·접근성·권한·중복·단일 DB 복원·migration·생성 타입·채팅 초기화와 회귀 검증을 통과한다. 문서 반영만으로 통과 처리하지 않는다.
- 비회원은 설문만, 회원 챗봇·이력은 본인에게만 허용.
- 완성 증상 목록만 게시되며 실제 추출은 사용자 지시 후 컴퓨터 유즈로 수행.
- 전체 문장·생략 항목·실제 별표 검토 뒤 조 단위 청킹·임베딩.
- RAG 선행·근거 부족 시 안내 불가·연락처 없는 직접 문의·외부 검색 없음.
- API 계약·프론트 타입·단일 migration·Docker 이미지와 1개 워커 설정이 일치.
- 3~5년 보존·명시적 삭제·GROUP BY·복원 절차가 일치.

확장 결정은 [확장 판단 기준](../architecture/scaling.md)을 따른다. 검색 지연·API 자원·배치 반복 실패·DB 경쟁·무중단 요구가 확인되기 전에는 큐·다중 워커·DB 분리·고가용성 구성을 운영하지 않는다. 실행한 검증과 남은 제한은 출시 기록에 남긴다.
